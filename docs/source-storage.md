# Storage, downloads, settings, and lyrics port notes

The Android tree at `../Metrolist/Metrolist-main` was inspected read-only. The references below identify the actual implementations used for this port rather than assumptions about YouTube Music.

## Integration contracts

`LibraryStore` does not own a UI thread. Await mutation methods before refreshing UI lists. `State.Settings` and `State.Session` are mutable to permit a single UI owner to update a snapshot before `SaveAsync`. Do not mutate lists from multiple threads. Store methods serialize persistence with a semaphore. Likes, playlists, and history roll their in-memory mutation back when persistence fails or is canceled, so a reported failure cannot be silently committed by a later exit save. The application should save the queue on meaningful changes and pause/exit; it should not write every playback tick.

`DownloadService` does not dispose the shared `HttpClient`. `DownloadAsync` accepts a resolved audio URL, streams to a temporary file, verifies the declared content length when present, rejects text/JSON responses, commits audio, then commits metadata. Googlevideo hosts use the shared `HttpRangeStream` and finite 256 KiB range requests: live testing found that unrestricted full media responses could reset before completion. Other hosts retain ordinary response streaming. The copy buffer is rented at 64 KiB; no full track is loaded into RAM. It saves track metadata, not signed stream URLs. Progress reports are throttled to 250 ms while copying. `FindDownloaded` permits playback without contacting the music service. AAC/MP4 is the desktop playback format; this service does not transcode media. The optional cache and explicit downloads have independent budgets.

`LyricsService.GetAsync(Track, cancellationToken)` returns `null` for a successful search with no matching lyrics. Network, permission, timeout, and parsing errors remain observable to the caller. Cache write failure does not prevent display. `LyricsDocument.GetActiveLine(position)` returns `-1` before the first timestamp. The caller can reuse its playback progress notifications rather than starting a second lyric timer.

## Resource characteristics

- No database engine, ORM, service container, file watcher, download daemon, lyric polling loop, or dedicated worker threads are added by these components.
- One active download per `DownloadService` bounds network concurrency and buffer memory. A single buffer is rented only while copying. Downloads remain available after application restart through their manifests.
- Explicit offline audio and optional cache are bounded separately. Lowering the cache budget and calling `TrimAsync` evicts cached audio; explicit downloads require user removal if the limit is reduced below usage.
- History is bounded at 500 entries. Likes and playlists preserve all user entries; their JSON metadata snapshot is fully resident and rewritten on mutation. Large-library indexing is a documented future improvement, not a claim of constant-memory storage.
- Credentials are protected for the current Windows user. Another process running as the same user can decrypt DPAPI data; this is the normal DPAPI security boundary.
- Credential file operations are serialized. The view model also serializes the complete save/sign-out action, including client authentication and status updates, so a pending save cannot reactivate the previous account after sign-out. Startup initialization is tracked and drained before resources are disposed; closing before queue restoration retains the previous durable queue and playback preferences.

## Incomplete parity and limitations

- Android Room database import/migration, smart playlists, album/artist library relationships, playback statistics, remote sync scheduling, cross-device merging, upload management and multiple-account profiles are not implemented by the local storage layer.
- Only the LRCLIB provider is ported here. BetterLyrics, KuGou, Paxsenix, LyricsPlus, Zemer, YouTube caption fallback, translations, romanization, TTML, word highlighting and background singer rendering remain absent.
- Cache files are complete AAC tracks. Media3's shared partial-byte-range streaming cache, interrupted-download resume, automatic retry of expired URLs and browser session extraction are not implemented here. A canceled/error download is cleaned up and can be retried from the UI.
- A process crash can leave a `.part` file; normal cancellation/error paths remove it. These files are not treated as downloaded tracks. The application may remove old orphan parts during maintenance; no recurring cleanup task runs.
- Download media files use a stable SHA-256 key derived from the track ID. They are app-managed offline files, not tagged user music exports.
- The local metadata store assumes one application instance and one UI owner. Atomic replacement protects against partial saves, but it does not merge simultaneous saves from two independent application processes.

The LRCLIB endpoint was checked against [the provider's API documentation](https://lrclib.net/docs); behavior and selection algorithms above are grounded in the supplied Kotlin implementation.

## Verification

`tests/Metrolist.Tests/StorageTests.cs` exercises persistence across store recreation, duplicate playlist removal, history de-duplication, canceled saves preserving the original file, locked-file save failures rolling back every library mutation, corrupt-file preservation, DPAPI roundtrip/plaintext absence/sign-out, streamed download quota/duplicate/truncated/cancellation cases, cache eviction, lyric selection and persisted cache reuse, LRC offsets/fractions/repeated timestamps and active-line lookup. Googlevideo fixtures reject unrestricted full requests and verify a three-range download byte-for-byte, reuse without additional requests, mid-range cancellation cleanup and document-response rejection. Headless checks exercise concurrent save/sign-out state, closing during startup with a large saved queue, and a clean production-view screenshot without fixture tracks or playlists. These deterministic HTTP fixtures are test data and never appear in production features. Live network and UI verification are recorded in the main progress document after execution.

On 2026-11-10 the combined solution built under stable SDK 10.0.404 with zero warnings and errors. The deterministic suite passed, including all new range-download and rollback cases. The isolated headless suite passed mouse/keyboard navigation, settings and playlist persistence, concurrent account save/sign-out, shutdown during a 10,000-entry queue load, resizing, and a 4,096-song list with only six realized row controls. The clean startup screenshot at `docs/screenshot.png` was rendered with the production XAML and inspected after capture. These tests do not establish real YouTube audio decoding; that is verified separately by the native playback tests.
